# AUD-01 — supported photo clients and legacy revocation

September 13, 2026. B02h is an evidence/rollout-contract slice, **not** a production rekey or closure of AUD-01. [Measured synthetic evidence](evidence/b02h-revocation-qc.json). Related AUD-20 supported-client retirement; do not silently retire installed clients.

## Supported delivery contract
Cookie-web and new anonymous share delivery already reauthorize every new image request. B02g adds opt-in `X-CellarSnap-Photo-Delivery: request-v1` bearer payloads and mobile rendering/crop reads. The new source never needs a Storage read signature for a wine photo. It sends bearer credentials only to the exact configured app image endpoint, with no cookie fallback for explicit bearer, no-store bounded bytes and current `can_access_wine_photo` authorization. Original dimensions remain available for cropping. Mounted bytes, screenshots, in-flight authorized responses and retained client copies cannot be recalled by changing server policy.

An installed binary is not considered adopted just because its source merged or its Expo export passed. Record the binary/OTA identifier, supported platform/runtime, tested authentication and upload/gallery/crop behavior, distribution state and actual installed-version adoption before retiring the old response contract. No minimum installed native version or cutoff date is set by this document. Web cross-origin image fetch is tested; any Expo web hosting needs its established authenticated API proxy/CORS configuration too.

## What the hosted measurement proved
A disposable label object was uploaded with a one-hour requested cache control and 600-second raw and transformed signatures. Both warmed from MISS to HIT. After its source entry/photo became private, both exact URLs still returned HTTP 200 and the same bytes. A hash-verified copy was created at a new key, synthetic row references moved, and the old object deleted through Storage.

Both old URLs still returned cached HTTP 200 at 0, 5, 15 and 30 seconds after deletion; both returned HTTP 400 at 60 and 90 seconds. The new object stayed readable and hash-identical. Fixture rows and both paths were cleaned up. No ordinary user object, account flag or signing key changed in this measurement.

This brackets observed byte revocation to **(30, 60] seconds on one execution host**, not an exact duration or worldwide SLA. Existing browser/native retained copies and other CDN regions were not measured. Fresh signatures, token TTL changes, no-store request headers and privacy-only updates are not a substitute for revoking existing object capabilities. [Supabase Smart CDN](https://supabase.com/docs/guides/storage/cdn/smart-cdn) documents object deletion invalidation and distinguishes it from token expiry. The current changelog was checked; no relevant hosted Storage API breaking change was identified.

## Required production implementation before AUD-01 closure
1. Establish and distribute supported request-delivery clients. Measure legacy payload/direct SDK read consumers with sanitized version counts. A version header is capability negotiation, not proof that all active clients adopted it. Existing direct Storage signing remains possible for authorized old clients until a reviewed authority cutover prevents newly minted capabilities.
2. Inventory every source and copied reference: `entry_photos.path`, three `wine_entries` image paths, `entry_group_slides.path`, `profiles.avatar_path`, collection item label/preview snapshots, collection cover paths, and `__original` crop siblings. `public_profiles` derives its avatar path; do not mutate the view. Review reference URLs and external consumers separately. Preserve original/shared-copy source ownership and privacy semantics.
3. Implement a bounded, resumable rekey command with a durable operation record and stable old/new key mapping. Copy first via Storage, verify size/hash/type, then atomically compare-and-swap all canonical/derived database references under the relevant source locks. Reject/retry conflicting uploads/crops/edits. Never delete an old object until every required reference commit and new-object access check succeeds.
4. After reference commit, delete the old object via Storage and record deletion confirmation plus multi-region raw/transformed denial observations. Failures leave a resumable pending-revocation operation; do not report completion or roll references back to a retired old key. Cleanup/retry must tolerate lost responses and previously completed steps. A DB transaction cannot make external Storage operations atomic.
5. Couple future privacy/block/test-author/lifecycle changes to the retained-capability contract. A one-time rekey cannot fix newly minted legacy URLs. Remove or constrain legacy signing only after client compatibility is proven, preserving legitimate source-owned uploads and crop/copy operations.
6. Run owner/friend/block/test/anonymous/shared-copy matrices, concurrent upload/crop/rekey races, lost-response/rollback/retry, image hashes and original-source checks, and actual native runtime acceptance. Release in small observable cohorts. Define a measured revocation objective without promising recall of retained bytes.

Global key rotation, bulk object rewrite/deletion, cache purge, forced logout, native cutoff and mass data repair are **not implemented or performed** by B02h. The next production slice is the resumable inventory/rekey implementation plus client/authority adoption decisions above. Preserve the P0/Partial status.
